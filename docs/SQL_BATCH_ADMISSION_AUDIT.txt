SQL 批量登记优化、日志碰撞修复与 dev 验证（2026-11-24）

改动与边界
1. GlobalCronBudget.pump：同一个 IMMEDIATE 写事务里的 N 次逐条排队登记，改为每块最多 200 行、600 个绑定参数的 INSERT SELECT。全部分块仍在同一事务中，提交成功后才标记 registered；queued 条件、token 和 ON CONFLICT 去重保留。
2. CronExecution.runSingle：所有手动执行日志文件名追加每次启动独立 UUID。毫秒时间戳可能相同，多实例任务的 submission token 也可能被同一批不同任务共享，因此不能用二者充当独立日志身份。普通任务和多实例任务统一使用运行专属文件名。
3. 普通 CRUD 继续 ORM；原生 query 调用点数量仍为 134。没有新增索引或迁移，没有削弱事务、回执、执行许可、取消/超时/恢复检查。
本轮源码/测试增量：2 个生产方法、4 项新增测试，见 scope.json / change.patch。

SQL 排查与取舍
批量登记有可量化的往返成本，已优化。预算快照中的进程存活、继承运行和配置读取继续保留，避免缓存滞后破坏全局上限。排队排名继续短任务优先及 30 秒老化；不截断可能包含死 owner 的排序集合。
退出结算/记账继续保留 affected-row 门控、回执冲突判断和原事务边界。已有运行实例 active 部分索引，本轮没有为局部读取增加写放大。
50000 历史记录下实际 SQL 的 18 份 EXPLAIN 见 query-plans.json：登记和退出查询走主键；预算继承运行/排队排名走 cron_trigger_running_task / cron_trigger_queued_task 部分索引。排名使用临时排序是动态老化语义所需；未新增历史表全表扫描。

真实脚本对比协议
隔离容器 2 CPU /1536 MiB /512 PID，全局任务上限 4。真实 Python/JS/Shell CSV、JSON、压缩、哈希及文件操作，交替 stdout/stderr UTF-8 标记，逐行校验内容及顺序。18 任务=9 长9 短；72 任务=12 长60 短，后者配比在任何 72 任务采样前固定。
CPU 为 cgroup CPU 秒/轮均值；内存为每轮采样峰值均值；短任务 P95 为提交至脚本第一行的全部短任务样本按 nearest-rank 汇总。不是各轮 P95 的平均。排队 P95 单独计算。预热只排除性能统计，仍核对可靠性。

发现并修复的日志完整性问题
第一轮故障验收在 JS HTTP worker SIGKILL 场景中失败：cron 100 和102生成相同 perf3_fault/2026-11-24-04-21-48-274.log。各自独立账本只执行一次、输出200行，但同一文件混写400行。没有把该失败当成通过或删除它。证据：log-collision-records.json、父目录 bench/final-other-js-http 的输出/账本及 results/other-faults.log。
修复前源码的固定毫秒回归：普通任务三个执行只生成1个文件；多实例不同任务共享 token 时两个路径相同。修复后两项均通过，普通任务真实子进程日志分别完整，路径安全测试也通过。
仅修普通任务的中间日志版本补测被主动中止，发现多实例 token 也共享后统一修复；中止数据保存在 log-fix-v1-incomplete，未纳入最终版本结论。
