# 定时任务执行：第一版优化方案与验收

目标：用户设定一个时间后，能知道规则是否已生效、这一轮何时被调度、为什么等待或跳过，以及最后一次执行的结果。短等待是核心体验；同时要保住该跑的任务，并看得见那些没启动的任务。只比较已启动任务的平均等待，会让“丢掉慢任务”的实现看起来更快。

青龙已有脚本环境、系统 crond、秒级 Node 定时、手动运行和订阅生态。第一版沿用它们，先解决同一配置在不同入口解释不同、执行过程查不到、无法从运行记录核实统计次数的问题。

## 已落地的实现顺序

1. **规则发布。** 系统 crontab 写入或安装失败时，API 返回失败，保留待同步标记，触发调度器恢复。失败期间旧系统规则仍可能执行。系统规则转交 Node 时先移除旧规则，确认后才注册新规则；其他任务保存成功不能替它确认注册。
2. **统一时间。** 表单预览、列表、详情从服务端获取时间。常规和附加规则共享 Node 注册使用的日历与兼容过滤，列表取所有规则中最早的下一次。停用、待同步、手动和开机任务没有下次定时。保留系统 crond 可执行的五字段子集；扩展表达式和启用管理策略的规则走 Node。
3. **能查看每次触发并核实执行结果。** 每次可观测触发保存来源、可取得的计划、入队、派发、脚本入口和结束时间、状态、原因及可用的日志路径和退出码。任务详情可分页追踪。Shell 报告以触发 ID 关联；日统计通过 SQLite 原子累加，相同触发 ID 的重复上报只计一次。旧客户端由能定位实例的退出回执结算。升级时按已有退出记录与日汇总补足可证明的缺口，匿名统计重试仅作确认。已有日汇总保留在原入账日。同一任务和结果先抵扣当天可能对应的退出，多余的匿名次数按从近到远的顺序抵扣较早日期，每次最多使用一次。缺少耗时样本的补计只参与次数和成功率。
4. **减少没有价值的等待。** 任务可分别开启“上一轮仍在排队或运行时跳过”和最长排队时间。前者抑制同一任务的重复定时触发，不让它们排到其他任务前面；后者限制一次排队的有效期。两者是跳过策略，不能缩短脚本的实际运行时间。默认维持已有 FIFO、并发和单任务积压上限。手动及开机运行沿用手动队列，不会因定时跳过策略被丢弃。
5. **有限补跑。** 默认关闭；配置 1–86400 秒后，在全量恢复时只检查每条规则在窗口内的最近一次，且不得早于最近一次创建、编辑或启用。任务 ID、规则序号、表达式和计划时刻组成稳定 ID，正常触发和补跑争用同一条记录。已经启动、执行完毕、结果未知或因策略跳过的轮次不自动重放。用户主动再次运行是一次新触发。

## 如何判断等待是不是变短了

| 指标 | 口径 | 应如何解释 |
| --- | --- | --- |
| 排队等待 P95 | 当天观察到、且既有入队又有启动记录的触发，取“启动 − 入队”的第 95 百分位；毫秒，无样本显示 — | 衡量已获执行机会的任务排了多久。启动取调度器开始派发进程的时间，不代表脚本已完成初始化。 |
| 准时触发率 | 调度器按时收到的次数除以按规则推算的应触发次数 | 漏触发和迟到降低准时率。按时收到后被策略跳过，会同时记入按时触发和触发后跳过。 |
| 计划到脚本入口 P95、五秒内到达入口 | 对有计划时刻与脚本入口的触发，计算毫秒延迟分布和五秒内抵达的比例 | 同时显示入口样本数。手动和系统 crond 任务的可观测耗时见任务详情。 |
| 观察数、跳过数及原因 | 当天的触发记录；区分重叠、重复、积压上限、等待过期、配置变更和重启 | 与 P95 一起看，防止以跳过变多换取漂亮的等待数字。某任务的当前等待以及终态可在详情中查看。 |

例如 08:00:00 计划、08:00:01 入队、08:00:11 启动：调度唤醒延迟 1 秒，排队 10 秒，计划到启动 11 秒。此时优先看占用执行槽的任务；提高并发可能让 CPU、内存或下游接口更拥挤，无法凭这个样本判断应当扩容。

本地做了一个可解释的对照：并发槽为 1，暂停队列后依次提交某任务 5 次（每次执行真实的 `/bin/sleep 0.1`），再提交一个独立任务并放开队列。三轮中，独立任务在默认 FIFO 下分别等待 557、575、565 ms；开启重复跳过后分别等待 117、112、110 ms。每轮都少执行了 4 次重复任务。这说明队列被可丢弃的重复工作占满时，跳过策略如何让另一任务早点启动；如果 5 次都必须执行，就应保留默认策略。该实验用单机内存 SQLite 记录时间，不代表生产 P95。

## 验收与发布边界

- 对真正的 SQLite 文件并发发送当天首次与后续完成报告，核对成功、失败、总次数、总耗时、最大耗时及重复报告去重。
- 注入系统安装失败，观察创建、修改、停用、跨调度器转交，再恢复快照。使用假 crontab 安装器，不改开发机的真实 crontab。
- 用同一组日历边界在 UTC 与上海时区验证宏、主/附加规则、月末、闰年及日期/星期语义。升级 node-cron 时必须重跑：指定历史游标的预览依赖当前锁定版本的日期匹配器。
- 堵住真实单槽队列，验证重叠、积压、排队过期、同任务合并以及另一任务仍能执行；被拒绝的任务没有启动脚本。用 protobuf 恢复请求和真实子进程验证重复恢复后只写一次文件。
- 仪表盘的“今日系统定时任务（crond）”单独展示系统计划和实际触发记录。已确认安装的五字段规则按生效区间和面板时区枚举计划分钟，用系统执行命令行采集的派发分钟、任务 ID、规则匹配回执。包装进程延迟或跨日入库仍可核对这一分钟。仅有旧包装进程时间的回执保留为分钟归属待核实。安装未确认、时区不一致和夏令时切换日保留为待核实。旧格式回执有脚本入口或已核实退出证据时可计入实际启动。每个计划分钟只匹配一次，多余触发和未匹配回执分别展示。
- 手动池和定时池分别记录入队时的并发上限、占用数和最早占槽的八个执行实例。仪表盘展示等待最久的 25 条，等待期间随并发上限与实际占槽实例更新最近采样。取得执行槽即固定等待时长，命令准备时间单独留在后续时间线上，结束后可回看入队快照。
- 数据按已有运行实例保留天数清理，只清理已结束记录；清理为零天时不删。触发记录的去重受保留期约束。网络请求、转账等外部副作用不能靠面板保证只发生一次，需要脚本与下游自行做幂等。
- 部署到不同规格的机器后，可用同一组脚本复测等待 P95、准时率和跳过原因，决定是否调整并发或任务策略。

## 2026-11-13 Linux 容器验收

在 Docker Desktop 的 Linux ARM64 容器内启动完整青龙面板，使用 Alpine 3.24.4、BusyBox crond、Node 24.22.1 和独立的 SQLite 数据库。容器限 2 核、1 GiB，调度并发设为 2，时区为上海。运行的是本次工作区重新编译的后端和 Shell，基础镜像的依赖锁文件与仓库一致。

**真实 crond 与重启。** 通过面板 API 安装每分钟执行一次的脚本，核对系统表及脚本实际写入。将这一规则改成秒级时，故意让 BusyBox crontab 使用不存在的 spool 目录，安装实际失败。API 返回 503，任务标记为待同步，旧表仍保留原记录。撤掉故障后，后台自行恢复，系统活动条目数变为零，Node 开始执行。切回五字段规则并重启容器后，crond 在下一分钟执行一次。再次切到 Node 并重启，跨过下一个整分边界观察到 18 个不同计划时刻，crond 活动条目始终为零。整个实验里脚本实际留下 22 条不同的记录，正好对应 2 次系统执行和 20 次 Node 执行。

**负载与计数口径。** 四个脚本均通过面板 API 注册，由真实定时器启动。Shell 轮询等待 3 秒以模拟外部 I/O，Python 运行 12 万轮 PBKDF2，Node.js 序列化、解析并筛选 2 万条 JSON 数据，另一个 Shell 脚本写入并读取 1 MiB 临时文件。错峰组每个脚本运行 6 次。同秒拥塞组在 30 秒内每秒触发轮询，其余三项每 5 秒触发一次；对照组仅为轮询开启“上一轮仍在排队或运行时跳过”。两组均使用 2 个执行槽，并允许任务多实例运行。P95 对有启动记录的样本取最近秩；准时率用计划后 5 秒内启动数除以全部预定时刻，包括跳过的轮次。每组都按配置枚举计划时刻，与落库记录逐个核对。

| 场景 | 计划时刻 | 成功完成 | 跳过 | 排队 P95 | 计划后 5 秒内启动 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 错峰运行，默认策略 | 24 | 24 | 0 | 130 ms | 24/24（100%） |
| 同秒拥塞，默认策略 | 48 | 35 | 13（积压上限） | 9,512 ms | 5/48（10.4%） |
| 同秒拥塞，仅轮询开启重复跳过 | 48 | 26 | 22（已有轮询排队或运行） | 787 ms | 26/48（54.2%） |

拥塞两组中，轮询之外的 18 次任务都成功完成，其排队 P95 从 8,063 ms 降至 1,559 ms，五秒内启动从 3/18 升至 18/18。轮询本身成功执行的次数从 17/30 降至 8/30，是否启用此策略取决于业务能否丢弃中间轮次。

三组负载的 120 个计划时刻均逐项对上触发 ID 和计划时间。计入切换与重启实验后，13 个任务共 142 条记录，其中 107 次成功、35 次跳过；每个任务的每日统计与其完成数一致。当天仪表盘与独立读取 SQLite 的计算一致：105 个可测等待样本，排队 P95 为 7,688 ms，有计划时间的 140 次触发中 75 次在五秒内启动。两次系统 crond 触发按设计没有计划及入队时间。以上是该容器单轮各场景的实测值。

## 复审意见与下一轮优先级（2026-11-13）

此前的 Linux 验收证明了正常发布、跨调度器切换、成功回报及指定负载下的等待表现。复审在另一份干净的 Alpine 容器中测试了并发争抢、完成回报故障、在线全量恢复。以下 P1 表示建议列为正式发布前的修复项；P2 表示有明确影响的后续改进。下表保留修复前的复现步骤和验收条件。修复结果见文末。

| 优先级 | 实际触发条件和结果 | 建议改动与验收条件 |
| --- | --- | --- |
| P1 单实例可重复执行 | 关闭多实例，执行并发设为 4，让主规则和附加规则同秒到期。两个不同 PID 在同一秒写入开始标记，3 秒后都正常退出。两条触发各有合法 ID，但当前检查任务状态与登记本轮启动之间可以交错。 | 在派发进程前，按任务原子取得单实例执行权，以本轮标识释放。两条规则都要留记录，脚本只执行一次，另一轮标为重叠。覆盖手动与定时交错、已停止或失联的旧实例，并单独确定系统 crond 的执行约束。同步修订表单中“自动停止旧任务”的文案，当前 Node 路径意图是跳过新一轮。 |
| P1 回报中断时失败会记成成功 | 真实脚本写入标记并退出 17，故障仅阻断 Shell 到状态及日统计两个上报接口。Node 最终记录了成功、退出码 0，当天该任务没有统计行。外层 task 的正常收尾固定返回 0。 | 托管执行透传脚本结果，覆盖直接输出、日志重定向及 tee。让调度父进程与 Shell 使用同一触发 ID 幂等结算在本地可确认的终态和统计。验收时分别断开两个接口、同时断开、恢复后重复回报，均只记一次失败，退出码为 17。系统 crond 缺少父进程兜底，须另行验证可重放回执或明确标记未确认。 |
| P1 恢复连带跳过无关任务 | 并发为 1，任务 A 占槽，任务 B 已入队。另一条系统规则安装失败后自动全量恢复，B 的定义和启用状态没变，却被标为 `skipped/changed`，实际脚本未写入。恢复时替换全部定时器，使原队列里检查注册对象身份的回调失效。 | 全量恢复按有效定义对比，保留未变任务的注册及已入队请求，只撤销确实变更、删除或停用的任务。以 A、B 和无关规则分别验证在线恢复、编辑 B、停用 B 及重复恢复，B 的副作用次数应依次为 1、旧定义 0、0、最多 1。 |
| P2 超时记录继续阻止新触发 | 同时开启最长等待 2 秒和重复跳过。第一轮已记录 `queue_timeout`，第二轮仍立即得到 `pending`。当时执行槽约 1.2 秒后释放，早于第二轮自己的截止时间。 | 超时后释放该请求的等待资格，并防止它随后被执行。验证第二轮可以等到槽位，已超时的第一轮不会挤占重复触发名额。 |

创建系统任务时还验证了“先返回 503、自动恢复后再原样提交”。再次提交返回 409，数据库和系统表中各有一条。这里的产品问题是调用方很难从报错定位已经创建的任务。建议在待同步响应中提供任务 ID 和可查询的应用状态，保留安装失败的反馈。

### 对验收标准的修订

- **区分业务义务。** 全部 48 个计划时刻依然要对账。对于保证执行的 18 个非轮询任务，另报成功 18/18、准时 3/18 或 18/18。对于允许跳过的轮询，另报执行次数、最长未成功间隔和跳过原因。避免把少执行轮询所得的 P95 改善解释成整个平台吞吐提升。
- **下一轮拥塞实验保留全部工作量。** 在同一资源配额、相同脚本和相同到期顺序下，对照 FIFO 与按任务轮转，每组交替重复，报告成功数、完成全部工作的总耗时、等待 P95、最老等待以及长任务等待。再单独测开启重复跳过的负载。公平排队、优先级或扩容是否值得做，取决于这组结果。
- **明确可见范围。** 分别展示从计划到派发、从入队到派发、从派发到脚本开始；给每个指标附样本数。系统 crond 的不可测时间保持空值。基于已观察触发的比例无法揭示未留下记录的漏触发，故障验收继续用独立枚举的计划时刻、脚本副作用和日统计三方核对。

## 脚本入口计时与停止操作的最终验收（2026-11-13）

### 用户如何判断脚本何时开始

仪表盘“今日面板定时任务”按计划日期核对已登记的面板定时规则。调度器先保存变更，再记录实际启用、替换或取消定时器的时间范围。第一次全量登记是可核对历史的起点。如果切换期间服务中断，页面只统计规则归属明确的计划时刻。有到期时刻落入不确定区间时，页面提示覆盖不完整，并隐藏整体准时率。服务停机期间，已经确认生效且持续有效的规则仍会产生应触发次数。

每条规则使用与调度相同的日历推算已到期的时刻，再按任务、规则序号、表达式和计划毫秒匹配触发记录。最近五秒留给正在落库的触发。跨午夜补跑仍按原计划日期核对，迟到的记录可修正前一天的未收到次数。手动、开机和系统 crond 的执行可在任务详情查看。

| 指标 | 起止点与分母 |
| --- | --- |
| 未收到触发记录 | 应触发减去已有匹配记录的次数。迟到回执出现后重新计算。 |
| 准时触发率 | 调度器接收时间与计划相差不超过五秒的次数除以应触发次数。没有快照、没有应触发次数时不显示百分比。 |
| 触发后跳过、仍在排队、命令已启动、启动未确认 | 四项相加等于已触发次数。派发并启动可由命令 Shell 启动回报、目标脚本入口或绑定本次执行的已核实退出账目证明。只有启动回报带有命令进程启动毫秒。启动未确认包含启动失败、取消及没有可用启动回报的记录。 |

## 缩短 Node 脚本启动时间（2026-11-13）

之前的 585 ms 是 24 次混合任务“计划到脚本入口”的 P95。当时 6 次 Node 解析任务从派发到入口用了 460–561 ms。同一容器中的三个独立 Node 进程仅载入面板 gRPC 客户端就用了 144–257 ms。现在托管 Node 脚本首次调用 QLAPI 的 RPC 方法时才初始化传输、解析协议并建连。JS、ESM 和 TS 共用这个客户端。全局安装包的解析优先级、面板依赖来源和 mTLS 均有回归覆盖。

同镜像、2 CPU、1 GiB、并发 2，每版分别运行三轮。每轮 24 个计划时刻，Shell 轮询、文件读写、Python 哈希、Node 解析各 6 次。六轮按旧、新、新、旧、旧、新的顺序运行，均无跳过。每轮计划至入口 P95 依次为 551、288、467、582、563、274 ms。下表从各版本 72 条原始记录合并计算。

| 项目 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 计划到脚本开始 P95 | 582 ms | 467 ms |
| 计划到脚本入口中位数 | 144 ms | 146.5 ms |
| 入队到派发 P95 | 34 ms | 36 ms |
| Node 解析任务计划到入口中位数（各 18 次） | 522.5 ms | 272.5 ms |
| 五秒内到达脚本入口 | 72/72 | 72/72 |

另外各跑 10 次首行发起两个并发 QLAPI 查询的脚本，核对两个返回值。计划到脚本入口中位数从 662 ms 降至 255 ms，脚本入口到取得两个查询结果的中位数从 49.5 ms 增至 138.5 ms，计划到取得结果的中位数从 706 ms 降至 397 ms。各阶段分别取中位数。RPC 初始化失败会在首次调用处返回可重试的错误。

此前单轮探索中两版混合 P95 分别为 605 与 655 ms，当轮两类脚本出现了较慢样本。单轮 24 次的 P95 取第二慢的执行，容易随负载波动。这里的改善以交替运行三轮的合并数据为准。Node 最明显，Shell 和 Python 的启动路径仍可独立分析。[优化前的 Docker 仪表盘](../../output/playwright/scheduler-startup-20261113/before.png) · [优化后的 Docker 仪表盘](../../output/playwright/scheduler-startup-20261113/after.png)

### 旧客户端统计回执的归属

旧版 Shell 单独发送的 `POST /dashboard/record` 只有 `ref_id/code/elapsed`。相同报文既可能是网络重试，也可能来自结果和耗时相同的两次执行。服务端返回 `code: 200`、`data: { counted: false, reason: "missing_execution_identity" }`，不修改日统计，也不查找“最近运行”。只发送这种报文的客户端，应改为发送已分配的 `trigger_id`，或发送可核对的开始及结束状态。升级前已入账的匿名统计保留原入账日，升级迁移结合退出记录补足可确认的总次数缺口。

任务详情的「日统计」按面板时区显示最近七天保留的退出和入账记录。可辨认的旧退出需要成功或失败状态与退出码一致。同一退出留下的相同开始副本只认一次，身份冲突的记录不能当作独立执行。旧账同时有重报和漏报时，次数相等也不能确认逐笔对应。如果脚本开始秒数和面板保存开始的时间都晚于当日最后入账，已有当日次数不能对应这次执行。迁移扣除后续日期仍可用的同结果次数后才补记。无法确定原始更新时间或已补过的统计行仅按可证明的总数缺口处理。已执行过旧补计的数据库只追加新证据证明的差额。旧匿名次数、入账日期和耗时样本均保留，因此已入账次数可以高于已核实退出数。

日统计清理会在同一事务保存最早保留日期，后续放宽保留天数也沿用已清理的边界。迟到的退出回执仍可核实保留实例的结果，记账日期取该实例已保存的结束时间。早于清理边界的统计不会重新生成，跨越边界后才结束的长任务按结束日正常入账。旧补计版本没有保存日统计清理边界。升级时以全库最早保留的统计日期和昨天中较早的日期作为保守边界，旧迁移已经运行而当前缺少的任务日账也保留为空。这可能留下无法区分历史清理与漏报的缺口，可从仍保留的退出记录核对。

旧版 Shell 的开始与结束状态通过任务、PID、开始时间及可用的日志路径匹配实例。独立脚本的终态、触发记录和日统计在一个事务内提交；属于调度器进程树的脚本由外层完整命令结算。只有 PID、没有开始时间的退出回执不能据以关闭实例。旧 CLI 系统任务发送的 `legacy-system:<秒>:<UUID>` 在状态入口转换为同一个触发 ID。重放已结算的回执不会重复计数。

旧版 Shell 的退出回执可以先于开始到达。服务端直接保存终态和对应的运行历史，随后重试开始只会命中同一实例。相同 PID 和日志路径下，不同开始秒数区分不同执行。进程已退出或出生时间晚于所报开始时间时，单独的开始回执保留为“结果未知”，可由后到的退出码结算。旧协议时间精度为秒，若同一任务的 PID、日志路径和开始秒数全部相同，则报文本身无法区分两次执行；这类客户端应携带独立执行 ID。

新版 Shell 和本机 CLI 为每次独立执行生成一次 `execution_id`（`client-<UUID>`）。受调度器管理的执行沿用父进程的 `trigger_id`，系统 CLI 保留已有的 `legacy-system:<秒>:<UUID>` 格式。开始、退出和单独发送的统计回执共用本次执行的标识。带标识的回执等待响应超时后最多重发一次，重发使用原请求体。CLI 根据运行中的面板对首条状态回执的校验结果选择字段。只有服务端明确拒绝标识字段时才重发匿名开始；若旧面板明确拒绝退出码，CLI 会重发兼容的退出回执，并跳过独立统计请求。超时、认证失败或其他校验错误均不触发协议降级。

新旧客户端共用任务、PID、日志路径和开始秒数时，带标识的独立执行按 ID 结算，匿名回执只匹配兼容实例或经核对的托管执行。两个完全匿名且所有匹配字段都相同的执行仍然无法拆分。

任务摘要保存最近一次开始回执对应的实例。开始秒数相同时，最后登记的开始回执取得摘要；该实例结束前时长为空，结束后可以为 0 秒。缺少开始回执的同秒历史退出只记入自己的记录和统计。

### 磁盘写满、恢复空间与跨日重放

监督进程和回报进程先独占创建一个空文件，将执行 ID、退出码或信号、结束毫秒、SHA-256 校验值和随机后缀编码在文件名里。目录还能分配条目时，这一步就能留下完整观测。随后发布兼容旧面板的 JSON。新格式正文若只写出一部分，恢复时核对文件名校验值及正文的每一个已有字节。若恢复进来的正文和文件名各自校验通过但结果相互矛盾，两份证据均随该执行保留。回收目录继续携带原观测，移动后强杀也能恢复。

目录项无法创建时，存活的 Python 监督进程和系统 crond 包装脚本仍可将实际结束时取得的同一份结果提交 SQLite。两个位置都因容量不足无法写入时，生产者保留原观测并重试。SQLite 在创建回滚日志时可能返回 `SQLITE_CANTOPEN`，此时还要核实数据库文件系统确实耗尽可用块或 inode。生产者和容器在第一次成功持久化前一起终止，恢复只能将执行标为结果未知。触发记录和运行历史均隐藏未经确认的结束时间和退出码。带有原始退出结果的独立回报可以在空间恢复后补计。只有截断正文的旧格式回执仍需要其他证据。

### ext4 满盘和虚拟机断电

本轮在专用 ARM64 Linux 虚拟机内运行 Docker 面板。数据库和回执位于同一块 32 MiB 的独立 virtio 磁盘，格式为 ext4，块大小 4 KiB，共 1024 个 inode，保留块为 0。数据盘使用 QEMU writethrough 和 ext4 的 ordered 模式。将后台日志提交间隔延长到 600 秒，使依赖内核后台刷盘的错误可复现。每次断电均从宿主向专用 QEMU 进程发送 SIGKILL，使用原磁盘重新引导，并通过 Linux boot ID 确认内核已更换。控制文件位于独立根盘。

旧版发布函数成功返回时可以列出三个名字，立即断电后目录为空。现在，Node 和 Python 发布者在尝试写兼容正文前，同步含有执行 ID 和退出元组的目录项，以及回执目录在上一级的条目。目录同步失败时仍可用同一份观测走数据库回报。可写入兼容正文时，先同步正文，再建立链接并同步其目录。两种发布者分别断电验证，按旧协议直接打开正式路径，均读回与断电前一致的 JSON。空间只够存目录项时，恢复需要理解该格式的面板。Linux 对文件与目录分别提供同步语义。[掉电前后对照](../../output/playwright/ext4-power-review/checks.json) · [旧格式读取实测](../../output/playwright/ext4-power-review/legacy-read.json) · [Linux fsync 手册](https://man7.org/linux/man-pages/man2/fsync.2.html)

### 旧回执已经回收，迁移保存退出证据时断电

复现顺序为：原回执和触发记录均已清理，只剩绑定执行 ID 的已核实账目；迁移事务写入退出证据后、提交前断电；重启后日账清理先拿到写锁。原清理逻辑会删掉最后一份可比对的原结果。修复后，清理仍让日账按时到期，但会将旧账目的执行 ID、退出结果和结束毫秒保留到证据迁移提交。迁移与完成标记在同一 SQLite 事务写入，迁移本身不改日账。

Docker 中的同一任务共执行 17 个真实脚本，数据库位于独立的 ext4 盘。为构造旧库，验收镜像仅跳过证据迁移，真实结算、文件回收和历史清理照常运行。第一次强杀 Linux 虚拟机前，迁移事务内可见 9 条证据及完成标记，独立连接及重新挂载后均可见 0 条证据、无标记，原 9 条账目仍在。日账清理先执行，随后并发提交一组重复及冲突回报。一个执行已转入冲突表，重新运行迁移后有 8 条可比对证据和完成标记。第二次在提交后立即强杀，重挂载后的内容与提交时相同。[事务与重启快照](../../output/playwright/ext4-migcut/verification.json)
