# WebSocket 真实容器资源对照（2026-09-14）

本轮证明的是多连接场景下的短窗口 CPU 收益：两个副本均下降，容器平均 CPU 3.859% → 3.541%，下降 0.318 个百分点，约 8.25%。无客户端 CPU 没有改善，内存没有显示一致收益。不能用此前读取调用次数减少 95% 代替这一结论。

## 环境与方法

- Docker Desktop Linux ARM64，8 核、约 3.82 GiB 虚拟机内存。每版两个独立副本，各限 2 CPU、1 GiB 内存，memory-swap 与 memory 相等；5 秒真实 exec curl 健康检查不变。
- 两版使用相同依赖、前端、后端产物和数据种子。以当前 `818fa4a74` 构建候选，再仅将 WebSocket loader 替换为 `b0846b3e8` 实现构建基线；这不是整个 develop 与 PR 的累计对照。
- 四个容器均完成相同真实任务预热：成功/失败退出、1 MiB 日志、手动停止、五任务并发和秒级调度。预热后等待 60 秒。
- 先测无客户端 5 分钟；然后每个容器建立 20 个真实 WebSocket 连接，等待 60 秒，再测 5 分钟。连接使用面板真实登录和容器内 SQLite 认证数据，每 30 秒发送一次应用心跳，没有前端页面额外 API 轮询。
- 客户端在宿主机运行，不计入容器资源。四副本同机并行测量，并非独立物理机；没有强制 GC。每容器每阶段 61 个样本，Docker API 每 5 秒采样。
- CPU = 容器累计 CPU 时间增量 / 实际经过时间，100% 代表一个核心满载。工作集 = usage − inactive_file；匿名内存来自 memory.stats.anon。PSS 为 PM2、primary、gRPC、HTTP 四个 Node 进程之和，取窗口结束值。

## 解读

- 无客户端：容器平均 CPU 1.087% → 1.093%，未改善；匿名内存两副本中位数的均值 136.01 → 139.00 MiB。
- 20 连接：第一组 CPU 4.000% → 3.539%，第二组 3.718% → 3.542%，降幅分别约 11.5% 和 4.7%。HTTP 进程分项平均约 3.202% → 2.878%，主要下降发生在预期进程。
- 20 连接匿名内存均值 163.20 → 165.85 MiB，结束 PSS 均值 176.15 → 178.12 MiB，未显示内存节省。工作集副本间差异较大，不能把它单独归因于 JS 对象或代码改动；匿名内存和 PSS 也不支持内存优化结论。
- 以上均值是两个副本指标的算术均值，不是把两个容器占用相加。不同指标和不同轮次的节省量不能相加。
- 两个副本、单个五分钟窗口不足以建立长期统计保证；本轮确认多连接下 CPU 下降方向一致，不声称单连接、无客户端、长期内存或其他任务负载同样受益。8.25% 是相对值，绝对下降只有 0.318 个 CPU 百分点。

## 运行有效性

两个阶段全部容器健康，无重启、OOM 或 worker PID/启动时间变化；第二阶段 80 个连接始终保持打开。采样后各容器再次执行真实任务，验证退出码和完整日志。测试客户端结束后关闭，测试容器停止，保留镜像和测试数据以便复查。
